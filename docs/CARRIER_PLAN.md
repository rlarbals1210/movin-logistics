# 운송인 화면 실기능 구현 계획

현재 `/carrier` 는 Stitch 목업을 옮긴 정적 JSX다. state·fetch가 0개이고, 어댑터(`toCarrierCalls`)는 빈 배열을 반환하며, 백엔드는 `carrier_id` 를 무시하고 고정값을 준다.

목표는 [PROJECT_KNOWLEDGE.md](PROJECT_KNOWLEDGE.md) 의 운송인 흐름 중 **"다음 콜 후보 3건을 예상 실수령 기준으로 비교"** 를 실제로 동작시키는 것이다. 표면 운임 1위가 실수령 1위가 아님을 비용 분해로 보여주는 게 데모의 핵심이다.

트랙 F(프론트)와 트랙 B(백엔드)는 병렬로 갈 수 있다. 의존선만 지키면 된다.

| D3 | 비용 상수 기준 | (a) 탄소 산정 문서값 (b) 최종 기획안 데모 수치 | 아래 참고 — **둘이 서로 안 맞는다** |

### D3 상세 — 반드시 먼저 정할 것

최종 기획안의 대표 데모는 `부산→서울 운임 47만원, 유류 7.4만원, 공차 1.4만원, 실수령 38.2만원` 이다.
그런데 탄소 산정 문서의 확정 상수(11t 적재연비 4.0km/L, 경유 1,503원/L)로 부산→서울 약 400km를 계산하면 유류비가 **15.0만원** 이 나온다. 기획서 수치의 2배다.

- (a) 탄소 문서 상수 사용 — 산출 근거를 화면에 노출할 수 있고 질문에 방어된다. 대신 **발표 스크립트의 대표 수치를 새로 뽑아야 한다.**
- (b) 기획서 수치 하드코딩 — 발표 대본은 그대로지만 "이 유류비는 어떻게 나왔나" 에 답할 수 없다.

기획 원칙이 "적합도와 예측 산정 근거를 공개한다" 이므로 **(a) 를 권장한다.** 결정 전까지 F2를 시작하지 않는다.

## 트랙 F — 프론트엔드

### F1. 데이터 배선 (선행: 없음 · 예상 30분)

기존 코드에 이미 재료가 다 있다. 새로 쓰는 로직은 거의 없다.

**F1-1** — [lib/adapters.ts](../frontend/src/lib/adapters.ts) 의 `toCarrierCalls` 구현

```ts
export function toCarrierCalls(raw: unknown): 운송인추천콜[] {
  const src = 객체인가(raw) ? raw : {}
  const 목록 = 행목록(src['운송인_추천콜'])
    .map(추천콜로)
    .filter((c): c is 운송인추천콜 => c !== undefined)
  return 목록.length > 0 ? 목록 : 예시_추천콜
}
```

같은 파일의 `행목록` · `추천콜로` · `예시_추천콜` 을 그대로 재사용한다. `toPredictions` 가 이미 같은 일을 하고 있으므로 동작이 검증된 경로다.

**F1-2** — `frontend/src/features/carrier/useCarrierCalls.ts` 신규

- `GET /v1/matches/carrier/{id}` 를 `lib/api.ts` 의 `get<unknown>()` 으로 호출 → `toCarrierCalls` 통과
- 반환 형태: `{ 목록, 상태: 'loading' | 'ready' | 'error', 출처: 'api' | '폴백' }`
- 실패 시 `예시_추천콜` 로 폴백한다. `fixtures.py` 주석의 "모델이 죽어도 데모는 산다" 와 같은 방침이다
- StrictMode 이중 마운트 대비로 `AbortController` 를 쓴다

**F1-3** — [main.tsx](../frontend/src/main.tsx) 에 `warmUpApi()` 호출 추가

`lib/api.ts` 에 이미 있는데 아무도 부르지 않는다. Railway 콜드스타트가 데모 중에 터지면 첫 화면이 로딩으로 멈춘다.

**F1-4** — [CarrierScreen.tsx](../frontend/src/CarrierScreen.tsx) 하드코딩 카드 3장을 목록 렌더로 교체

로딩·에러·빈 목록 상태를 각각 그린다. 이 시점에는 아직 기존 카드 디자인 그대로, 데이터만 훅에서 온다.

> **완료 판정:** 백엔드를 껐다 켜면서 실데이터 ↔ 폴백 전환이 화면에 반영되는지 확인. `출처: '폴백'` 일 때 개발 중에만 보이는 표시를 둔다.

### F2. 실수령 계산 (선행: D3, F1 · 예상 40분)

**F2-1** — `features/carrier/vehicleProfile.ts` 신규

`운송인추천콜` 타입에 **톤급이 없고** types.ts 는 09:30에 동결됐다. 따라서 톤급은 콜이 아니라 내 차량 프로필에서 와야 한다. 즉 기획의 "운송인 사전 등록" 은 부가 기능이 아니라 실수령 계산의 전제다.

- 필드: 톤급(5·11·25), 귀가 희망 지역, 선호 시간대
- 저장은 localStorage. 해커톤 범위에서 서버 저장은 하지 않는다

**F2-2** — `features/carrier/economics.ts` 신규 (순수 함수만)

상수는 [PROJECT_KNOWLEDGE.md](PROJECT_KNOWLEDGE.md) 탄소 산정 표를 그대로 옮기고 **출처 주석을 단다.** 발표에서 숫자 근거를 물으면 답할 수 있어야 한다.

```
유류비(거리km, 톤급, 적재여부) = 거리km ÷ 연비(톤급, 적재여부) × 1503
실수령 = 예측_운임 − 유류비(적재) − 유류비(공차) − 톨비
탄소배출kg = 거리km × EF적재(톤급) + 공차거리km × EF공차(톤급)
```

반환은 합계 단일값이 아니라 **분해 항목을 전부 담은 객체**로 한다. UI가 근거를 노출해야 하기 때문이다.

주의: 기획서 데모 공식은 3항(`운임 − 유류 − 공차`)이고 톨비가 없다. 백엔드는 톨비를 주므로 4항으로 확장하되, 화면에서 톨비를 별도 줄로 분리해 표시한다.

**F2-3** — 검증

테스트 러너가 없다(`package.json` 에 vitest 등 미설치). 러너를 새로 붙이는 대신 `economics.ts` 하단에 dev 전용 sanity check를 두고, 3건 고정값에 대해 손계산과 대조한 값을 주석으로 남긴다.

### F3. 비교 UI (선행: D1, F2 · 예상 60분)

**F3-1** — `features/carrier/CallCard.tsx` — 실수령을 가장 크게, 비용 분해는 그 아래
**F3-2** — 정렬 기준을 예측_운임이 아니라 **실수령 내림차순**으로
**F3-3** — 표면 운임 1위와 실수령 1위가 다를 때 배지로 명시 (데모의 한 방)
**F3-4** — 산출 근거 한 줄 노출 — 연비 가정·유가 기준·거리 출처
**F3-5** — 기획 원칙 반영: 값이 없으면 추정하지 말고 `데이터 축적 중` 으로 표기

> **완료 판정:** 후보 3건 중 표면 운임 최고액이 실수령 1위가 아닌 케이스가 화면에서 눈에 보이는가.

### F4. 판단 기록 (선행: F3, B3 · 예상 40분)

**F4-1** — 콜 선택 버튼. 자동 수락은 **넣지 않는다** (최종 기획안이 명시적으로 폐기)
**F4-2** — 미선택 사유를 선택형으로 짧게 수집 (공차 과다 / 귀가 불가 / 운임 부족 / 시간대)
**F4-3** — `POST /v1/carrier/decisions` 전송. 실패해도 화면은 진행시킨다

### F5. (여유 있으면) 하단 탭 연결

지금 하단 6개 탭은 전부 장식이다. 최소한 홈 ↔ 후보 두 개만이라도 실제 전환되게 한다. 설정 탭은 F2-1의 차량 프로필 화면에 연결한다.

## 트랙 B — 백엔드

### B1. 추천콜 필드 확장 (선행: D2 · 예상 20분)

[fixtures.py](../backend/app/fixtures.py) 의 `운송인_추천콜` 3건에 추가:

- `공차거리km` — 실수령 계산에 필수
- `귀가가능` — 프로필의 귀가 희망 지역과 도착지 비교 결과
- `복화가능성` — 기획의 비교 항목

types.ts는 동결이므로 `운송인추천콜` 을 고치지 말고, `features/carrier/` 에 로컬 확장 타입을 둔다(파일 상단 주석의 지시사항).

### B2. 공차거리 실계산 (선택 · 예상 40분)

`.env` 에 `KAKAOMAP-API-KEY` 가 있다. 직전 콜 도착지 → 다음 콜 출발지 실거리를 뽑으면 고정값보다 데모 설득력이 크다. B1의 고정값을 먼저 넣고, 시간이 남으면 교체한다.

### B3. 판단 로그 엔드포인트 (선행: 없음 · 예상 15분)

`POST /v1/carrier/decisions` — `{콜ID, 선택여부, 사유}` 를 받아 200을 준다. 저장은 메모리 리스트로 충분하다. 기존 엔드포인트와 같은 방침(검증 느슨, 422 내지 않기)을 따른다.

## 최소 데모 컷

시간이 부족하면 **F1 + F2 + F3-1~3** 까지만 해도 데모는 성립한다. "실수령 기준으로 다시 줄 세웠더니 순서가 바뀐다" 가 보이면 핵심 메시지는 전달된다. F4·F5·B2는 있으면 좋은 항목이다.
